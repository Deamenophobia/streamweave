# Local Python engine

Streamweave offers two calculation engines behind the same canvas. **Browser** runs the TypeScript core in a Web Worker and remains the default. **Python** runs an optional service on your computer using NumPy and SciPy. Both implement the existing 15 modules and accept the same version 2 project files. Python adds a numerical-library extension point; it does not add arbitrary scripts or a MATLAB language.

## Install and use

From the repository root, with Node.js 22.12+ and Python 3.12 installed:

```sh
npm ci
npm run engine:setup
npm run engine:start
```

Setup creates `.local/engine-venv` and installs pinned dependencies from `services/engine/requirements.txt` with transitive constraints in `requirements.lock`. Set `STREAMWEAVE_PYTHON` to a Python executable if it is not on PATH. Setup uses that interpreter to create the environment; start/check use the override directly when supplied, so clear it after setup to use the created environment.

In another terminal, run `npm run dev` and open **http://127.0.0.1:5187**. Choose **Engine → Python · local service**. The service listens on **127.0.0.1:5191**; workbench origins on localhost or 127.0.0.1 at ports 5187 and 5188 are allowed. Production preview uses 5188. Stop the service with Ctrl+C.

Engine choice lasts for the current page session. Reload starts with Browser. Changing engines reruns the current graph without changing the document. A missing or incompatible Python service produces an explicit error; choose Browser to recover. There is no silent fallback that would obscure which engine produced a result.

![Python engine selected in the Classic workbench](../local-engine.png)

The status bar shows the selected engine, progress between nodes, elapsed engine time, and cache hits. **Cancel** stops accepting the current result and requests cancellation. Browser cancellation terminates its worker. Python checks cancellation between nodes and numerical chunks; an in-progress native library call must return first. Rapid edits replace obsolete runs, and an older response cannot overwrite the latest result.

## Contracts and numerical behavior

The TypeScript registry remains the source for module ports, parameter fields, defaults, and bounds. `npm run contracts:generate` exports `protocol/modules.json`; CI rejects a stale export. Both sides compare its SHA-256 digest and protocol version before calculating.

Python validates the complete document independently with Pydantic. Numerical modules preserve nulls, quality states, units, timestamp alignment, observation availability, sample standard deviation, and in-sample regression metadata. Rolling calculations use bounded NumPy blocks; linear fit uses centered and scaled SciPy least squares. Both use binary64 floating point, so tiny rounding differences are expected. Changing language does not automatically increase precision or validate a scientific model.

Cross-engine fixtures compare every result, with numeric tolerance of 1e-9 and exact structural/quality checks. Independent analytical fixtures also test known answers. This is evidence for the covered cases, not proof that either implementation is universally correct.

Project JSON remains version 2 and contains no engine connection or machine path. Results JSON adds engine ID, engine version, protocol version, contract digest, and numerical-library versions when available. Reopening the project works with either engine; bit-for-bit equality across numerical-library versions is not promised.

## Ownership and extensions

| Responsibility                              | Location                                                                                           |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Engine interface, selection, cancellation   | `apps/workbench/src/execution/contracts.ts`, `useGraphRun.ts`                                      |
| Browser worker adapter                      | `apps/workbench/src/execution/browserEngine.ts`                                                    |
| Local HTTP adapter and response validation  | `apps/workbench/src/execution/pythonEngine.ts`, `protocol.ts`                                      |
| Generated shared module contract            | `protocol/modules.json`, generated by `scripts/export-module-contracts.ts`                         |
| HTTP boundary and bounded job lifecycle     | `services/engine/streamweave_engine/server.py`, `jobs.py`                                          |
| Project validation, graph scheduling, cache | `models.py`, `graph.py`, `executor.py`, `cache.py` in the engine package                           |
| Numerical implementations                   | `statistics.py`, `transforms.py`, `alignment.py`, `tables.py`, `pressure.py` in the engine package |
| Build-time evaluator registration           | `services/engine/streamweave_engine/registry.py`                                                   |

To add a calculation, define its public contract and browser implementation in the core registry, generate the manifest, then add its Python evaluator to the focused numerical module and register it. Add an independent expected-value test and a cross-engine fixture. Do not branch on module type in the scheduler, HTTP service, or inspector. The Python dependency test rejects local cycles and numerical dependencies on service/job orchestration. See [Extension ownership](extension-guide.md).

## Resource and trust boundaries

The service receives only project JSON and returns calculation results. It accepts no Python code, file paths, remote source URLs, or credentials. It binds to loopback and checks Host, browser Origin, protocol, and per-page session IDs. These checks do not make it a hosted multi-user service or protect it from another process running as your local user.

Existing input limits remain: 12 datasets, 50,000 total rows, 20,000 rows per dataset, 40 columns per dataset, 50 modules, 120 connections, 1,000 observations per rolling window, and a 15 MB request. Python results are limited to 30 MB of encoded node outputs.

The service permits two active jobs and four retained job slots. Completed jobs expire after 60 seconds, pruned on later requests; the client releases each consumed or cancelled job. A job has a cooperative 120-second deadline, with a 125-second client deadline. There is no disk persistence. Two session caches each hold at most 16 MB of JSON-encoded outputs, evicting least-recently-used nodes. This bounds cache content, not total process RAM; Python objects, datasets, native arrays, and serialization require additional memory.

Cache keys include node parameters, input data, upstream dependencies, and contract digest. Moving nodes or renaming the project does not recalculate. A correlation-window edit invalidates that node and its descendants while retaining unrelated branches. Stop the service to discard all cached data.

## Verification and performance

```sh
npm run check
npm run engine:check
# With engine:start running:
npm run engine:benchmark
```

The benchmark writes `.local/engine-benchmark.json`. It measures the existing TypeScript core under Node, a warm Python engine, and complete local HTTP requests including JSON and 120 ms polling. It excludes UI rendering and interpreter startup. Warm-cache measurements include input validation and key generation. See the [validation record](../validation.md) for measured results and limitations.

Small calculations often favor Browser because Python incurs validation and transport costs. Vectorized calculations and cached branches can help larger or repeated studies, but the current rolling implementation still scales with rows multiplied by window length. Neither engine is an unlimited data-processing service.
